Problems Addressed
  • Single agents failing on complex multi-step workflows that exceed their context window or reasoning capacity

  • Multi-agent runs difficult to test: non-deterministic, hard to replay, impossible to debug without distributed traces

Details

The problem

A single-agent loop works well for tasks that fit in one context window and require one chain of reasoning. Enterprise workflows rarely fit this description. A customer onboarding process requires document extraction, identity verification, risk scoring, policy lookup, and response drafting — each a distinct reasoning task that benefits from a dedicated agent with its own tools and system prompt, not one overloaded agent trying to do everything at once.

When teams encounter this complexity, they typically do one of two things: they build a monolithic agent that fails unpredictably on longer workflows, or they build an ad-hoc multi-step pipeline with no shared state model, no failure recovery, and no observability. Neither is production-safe. A proper multi-agent architecture requires deliberate topology design: which agents are peers, which are supervisors, where state lives between steps, how failures propagate, and how a human operator intervenes when the orchestration needs it.

The four cross-cutting concerns

Regardless of topology, every multi-agent system must solve four problems that single-agent implementations ignore:

  • Shared state — where does context live between agents? Options range from passing full context in each handoff message (simple, expensive) to a shared state store (efficient, requires schema discipline). We design the state model as an explicit artifact, not an afterthought.
  • Failure recovery — when subagent B fails after subagent A has completed, does the orchestration restart from the beginning? From a checkpoint? Escalate to a human? Each failure mode needs an explicit policy. Without one, the default is silent failure or infinite retry.
  • Human-in-the-loop escalation — not every decision should be made without human oversight. The orchestration design includes defined escalation points: conditions that pause the workflow and route to a review queue, with a clear re-entry path after the human acts.
  • Observability — a multi-agent trace must be navigable. One Langfuse root trace per orchestration run, with one span per agent invocation, preserving the parent-child relationship between supervisor and worker spans. A failed run must be diagnosable from the trace without reading orchestration code.

What makes this different

  • Topology-first, not framework-first — most implementations choose LangGraph or AutoGen first, then fit the workflow to the framework. We design the topology from the workflow requirements and choose the framework to match, which avoids the most common source of architectural lock-in.
  • Failure modes as first-class requirements — we document and design for failure recovery before writing implementation code. Teams that skip this discover their failure policies in production at the worst possible time.
  • Deterministic test suite — by recording Langfuse traces as test fixtures, we produce a replay-based test suite that catches orchestration regressions without requiring live LLM calls. CI runs in seconds, not minutes.
  • Runbook included — operational documentation is part of the deliverable, not an afterthought. On-call engineers can diagnose and resolve most orchestration incidents without the original implementation team.

Client story

B2B software company, 600 employees, sales process automation — had built a single agent to handle inbound sales enquiry triage: classify intent, look up company data, draft a personalised response, and route to the right sales rep. The agent worked in demos but failed on 55% of real enquiries — context window exhaustion, tool call failures mid-sequence, and no recovery when the CRM lookup returned no results.

We redesigned the workflow as a four-agent supervisor topology: a classifier agent, a research agent (CRM + web), a drafting agent, and a routing agent — all coordinated by a lightweight supervisor that managed state and failure escalation. Implemented in LangGraph with Langfuse tracing and checkpoint-based recovery. End-to-end completion rate went from 45% to 93% in the first two weeks of production. The sales team received a runbook and resolved the first post-launch incident independently in 12 minutes using the Langfuse trace.

Risks we mitigate

  • Context window exhaustion — single agents accumulating context across a long workflow hit token limits and produce degraded output or fail silently. Specialised agents with bounded context eliminate this failure mode.
  • Silent orchestration failures — without explicit failure policies and distributed traces, a failed subagent leaves the orchestration in an indeterminate state with no indication to operators. Checkpoint-based recovery and Langfuse trace alerts make every failure visible and recoverable.
  • Unbounded cost accumulation — multi-agent runs with retry loops and no budget envelopes have produced five-figure API bills in production incidents. Per-run budget limits enforced at the orchestration level prevent this.

Common questions

How do we choose between LangGraph, AutoGen, and a custom orchestrator?
The choice depends on your topology: LangGraph suits stateful, graph-structured workflows with explicit checkpointing; AutoGen suits conversational multi-agent patterns; a lightweight custom loop suits simple pipelines that don't need a full framework. We recommend based on your topology design and existing team expertise — not framework preference.

What happens when two agents disagree on the next action?
Disagreement is a designed escalation path, not an error state. We define explicit resolution policies: majority vote, supervisor override, human escalation, or confidence-threshold routing. Which policy applies depends on the stakes of the decision. The policy is documented in the failure mode register and enforced in the orchestration code.

How do you test a system that calls an LLM non-deterministically?
We record real production traces in Langfuse and use them as deterministic test fixtures. The orchestration logic (routing, state transitions, failure handling) is tested against these fixtures without live LLM calls. Prompt regression is tested separately using Langfuse's dataset and experiment feature, which scores output quality against a curated eval set.
