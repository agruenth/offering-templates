Details

The problem

Retrieval-augmented generation is the most common pattern for grounding AI agents in enterprise knowledge. It is also the most commonly under-engineered. A naive RAG implementation — chunk documents, embed them, store in a vector database, retrieve top-k on cosine similarity — works acceptably on a curated demo corpus. It fails on real enterprise knowledge bases that mix document types, contain outdated information, and have access restrictions that must be respected at retrieval time.

The failure is rarely obvious. The agent does not error — it produces a confident, plausible answer that happens to be wrong because the retrieved context was irrelevant or incomplete. Without a retrieval quality metric tracked over time, teams discover this pattern through user complaints rather than dashboards, and cannot attribute the failure to its root cause: chunking strategy, embedding model choice, query expansion, or reranking.

Retrieval quality measurement

A RAG pipeline cannot be improved without measurement. We establish a retrieval eval suite as part of the engagement: a curated set of query–expected-document pairs drawn from real user queries and validated by domain experts. This suite is used to:

  • Benchmark the baseline pipeline (before any changes) to establish a documented starting point
  • Evaluate each configuration change (chunking, embedding, reranking) before deploying to production
  • Run in CI as a regression gate — no pipeline change ships if retrieval recall drops by more than a defined threshold
  • Produce a weekly retrieval quality score in Langfuse, tracked against the baseline and visible in the agent quality dashboard
MetricWhat it measuresTarget
Recall@k Fraction of eval queries where the relevant document appears in the top-k retrieved results ≥ 0.85 at k=5 for the production eval set
MRR (Mean Reciprocal Rank) Average inverse rank of the first relevant result — penalises correct results buried low in the list ≥ 0.75 on the eval set
Grounding score LLM-as-judge: does the agent's final answer make claims supported by the retrieved context? ≥ 0.87 on a sampled production trace set, measured weekly via Langfuse
Staleness rate % of retrieved chunks older than the defined freshness threshold for that document category < 3% staleness rate on production retrievals

Knowledge lifecycle governance

Retrieval quality degrades over time if the knowledge base is not maintained. We design a lightweight lifecycle process that runs as a scheduled pipeline:

  • Change detection — source document changes trigger re-ingestion and re-embedding of affected chunks. Document deletion propagates to index removal within a configurable TTL.
  • Conflict detection — chunks making contradictory claims on the same factual question are flagged for human review rather than serving both to the agent.
  • Freshness classification — document categories (policies, product specs, regulatory guidance) are assigned freshness thresholds; chunks exceeding their threshold are demoted in retrieval scoring or excluded until reviewed.
  • Ingestion audit trail — every chunk in the vector store has a provenance record: source document, ingestion timestamp, embedding model version, last validation date. Auditors can trace any agent response back to the specific document chunk that grounded it.

What makes this different

  • Eval suite before pipeline — we build the retrieval evaluation set in Phase 1, before writing any pipeline code. Every subsequent decision is measured against it, not validated by intuition.
  • Access control at retrieval, not at display — most implementations filter results in the UI layer. We enforce access at the vector store query level, so restricted documents never enter an agent's context window regardless of how the agent is called.
  • Lifecycle as a first-class deliverable — knowledge infrastructure without a maintenance process degrades. The change detection and freshness pipeline is part of the engagement scope, not a follow-on project.
  • Hybrid retrieval by default — pure vector search is inadequate for enterprise knowledge bases that mix narrative text with structured identifiers, codes, and names. Hybrid retrieval with BM25 covers both retrieval patterns without requiring two separate systems.

Client story

Healthcare provider, 3 200 employees, clinical policy Q&A agent — had deployed a RAG-backed agent to answer staff questions about clinical policies and procedures. Retrieval recall was unmeasured; clinicians reported that the agent frequently cited outdated policy versions or returned answers that could not be traced to any policy document. Legal and compliance had raised the issue of confidential HR policies appearing in answers to clinical queries.

We audited the corpus (1 400 documents, mixed formats), built a 200-query eval set validated by clinical staff, and measured baseline Recall@5 at 0.51. After redesigning chunking for structured clinical documents, switching to a domain-tuned medical embedding model, adding BM25 hybrid retrieval, and implementing per-document access classification, Recall@5 reached 0.88 and the grounding score reached 0.91. A freshness pipeline flagged 47 outdated policy versions within 48 hours of deployment. No confidential HR documents have appeared in clinical agent responses since access controls went live.

Risks we mitigate

  • Silent retrieval failure driving hallucination — the most dangerous failure mode: the agent answers confidently with no retrieved context, and no system raises an alert. Retrieval spans in Langfuse make empty or low-relevance retrievals immediately visible.
  • GDPR and access control violation — agents retrieving documents above the requesting user's clearance level is a data protection breach on every query. Access-level filtering at retrieval time eliminates this exposure.
  • Knowledge decay undermining trust — a knowledge base that gives correct answers at launch but degrades silently as source documents evolve destroys user trust faster than never deploying the agent. Freshness enforcement and change detection prevent this.

Common questions

Should we use a managed vector database or self-host?
Depends on your data residency requirements and operational capability. For regulated data that cannot leave your environment, we deploy pgvector or Qdrant on your infrastructure. For teams without database operations capability, managed services (Pinecone, Weaviate Cloud) reduce operational overhead. We recommend based on your constraints — both options are fully supported.

How do we keep the knowledge base current without re-ingesting everything?
The change detection pipeline monitors source systems for document updates and triggers incremental re-ingestion for changed documents only. Full corpus re-ingestion is only required when the embedding model changes. For most enterprise document corpora, incremental updates run in under 30 minutes nightly.

What if our documents are in multiple languages?
We configure multilingual embedding models (mE5, multilingual-e5-large, or Cohere multilingual) and validate retrieval quality separately per language using the eval suite. Cross-language retrieval — querying in English against German documents — requires additional evaluation and is scoped explicitly.
