Details

The problem

The Model Context Protocol (MCP), introduced by Anthropic in late 2024 and now adopted across all major LLM platforms, provides a standard interface between AI agents and the tools, data sources, and services they call. Without MCP, enterprise tool connectivity is a permanent integration backlog: every new agent project starts with three weeks of connector development before anyone writes a line of agent logic.

More critically, bespoke connectors accumulate debt. Credentials age. Rate limits are not enforced. Write operations have no dry-run mode. When an agent misbehaves, there is no audit trail — only application logs scattered across six different systems. And when the underlying API changes, six connectors break simultaneously.

An MCP server layer replaces this with a curated registry: each enterprise system exposed through one server, with typed tool definitions, enforced permissions, rate limits, and a dry-run gate for all write operations. Every agent in the organisation gets access to the same tool estate from day one — with governance built into the protocol layer, not the agent code.

MCP conceptWhat it doesGovernance value
MCP Server Wraps one enterprise system, exposing a set of typed tool functions. One server per system of record. Stateless; scales horizontally. Single integration point per system. Credential rotation happens in the server, not across 20 agent codebases.
Tool definition Each tool declares name, description, input JSON schema, output schema, and side-effect classification (read / write / destructive). Agents receive this as a contract. Agents cannot invoke operations that are not declared. Destructive tools require elevated permissions and log an approval event.
Dry-run gate Write operations execute validation and return a preview of the intended effect before committing. The agent must receive explicit approval to proceed past the gate. Eliminates unintended mutations. All approval events are first-class audit records.
Rate limits & quotas Per-agent and per-role call limits enforced at the server layer, not in agent code. Burst limits, daily quotas, and circuit breakers configurable per tool. A runaway agent cannot exhaust a downstream API's rate limit or generate unexpected API spend.
Server registry A versioned catalogue of all deployed MCP servers with per-role access policies: which agent identities can connect to which servers, and which tools within each server they may invoke. "Which agents could have read customer records this month?" is a registry query, not a code audit.

What you get

  • Deployed MCP servers — one per system of record in scope, running in your infrastructure with full typed tool definitions, credential management via your secret store, and rate limit configuration.
  • Tool registry — a versioned catalogue of all servers and tools with per-role access policies, deployed as a queryable service. Includes a UI for platform administrators to manage access without code changes.
  • Dry-run gates — all write and destructive tools wrapped with preview-and-confirm gates; approval events logged to your observability platform.
  • RBAC policy set — access policy definitions for each agent role class, stored as code, versioned, and enforced at the server layer.
  • Integration test suite — automated tests for each tool definition covering happy path, schema validation, rate limit enforcement, and dry-run gate behaviour. Runs in CI on every server change.
  • Server development guide — documented pattern for your engineering teams to build additional MCP servers independently: project structure, authentication pattern, rate limit configuration, registry registration, and CI/CD pipeline template.

What makes this different

  • Protocol-level governance, not code-level — permissions are enforced in the server layer regardless of which orchestration framework the calling agent uses. Agent code changes cannot bypass access controls.
  • Dry-run by default for write operations — most connector implementations do not have a preview mode. We build dry-run gates into every write tool at the server level so agent bugs and prompt injection attacks cannot commit unintended changes.
  • Registry as a product — the tool registry is a governed service, not a config file. Platform administrators can grant and revoke agent access through a UI without touching code or redeploying servers.
  • Handover built in — the development guide and server template mean your engineering teams can extend the integration estate independently. Future systems do not require a new engagement.

What we need from you

  • API documentation and sandbox access — for each system in scope, API documentation and a sandbox environment available from Week 1 of Phase 2.
  • Named integration lead — one engineer with deploy rights to the target environment and knowledge of the systems in scope, able to commit 3–4 hours per week.
  • Agent identity inventory — a list of all current and planned agent identities, their roles, and the systems they need to access, available from Phase 1.
  • Secret management platform access — configuration access to your HashiCorp Vault, AWS Secrets Manager, or equivalent, for credential integration in Phase 2.

Client story

Insurance carrier, 1 800 employees, 5 agent workloads — had three agents all accessing the same Salesforce CRM through three independent REST connectors, each written by a different team. Credentials were different, rate limit handling was inconsistent, and the compliance team had no way to audit which agents had accessed which customer records without reading three separate codebases.

We built a single Salesforce MCP server with 12 typed tool definitions, a dry-run gate on all write operations, and per-agent RBAC enforced at the server level. All three existing agents were migrated to the MCP layer in two weeks. A tool registry UI was deployed for the compliance team. Time to answer "which agents accessed customer record X in the last 30 days" dropped from a multi-hour manual audit to a 45-second registry query. Two subsequent agent projects onboarded with zero connector development effort.

Risks we mitigate

  • Credential exposure in source code — credentials embedded in agent repositories are a recurring source of data breaches. Centralised secret management via the MCP server layer with automated rotation eliminates this exposure vector across all agent workloads simultaneously.
  • Uncontrolled write operations — agents with unbounded write access and no dry-run mode have caused production data corruption in multiple enterprise AI programmes. Dry-run gates require explicit approval before any state change commits.
  • Connector drift — as underlying APIs evolve, bespoke connectors break independently and silently. One MCP server per system means one maintenance point; API changes are absorbed in one place and all agents benefit immediately.

Common questions

We use OpenAI — does MCP work with non-Anthropic models?
Yes. MCP is an open protocol supported by OpenAI, Google DeepMind, and all major orchestration frameworks including LangChain, LangGraph, LlamaIndex, and AutoGen. The servers we build are model-agnostic. Changing your underlying LLM does not require rebuilding or reconfiguring any MCP server.

What about systems that don't have a REST API?
MCP servers can wrap any callable interface: REST APIs, GraphQL, gRPC, JDBC connections, and legacy SOAP services. For mainframe or proprietary systems with no API, we design the server against whatever interface is available, including file-based or message-queue integrations. The tool definition contract remains the same regardless of the underlying transport.

Can we add more servers after the engagement without bringing you back?
Yes. The server development guide and project template are designed for your engineers to use independently. Typical team ramp-up to build a new MCP server is one to two days once the pattern is understood.
