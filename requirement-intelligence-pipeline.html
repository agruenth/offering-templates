Details

The automotive RE problem

In automotive development the V-Model is not an abstract methodology — it is the contractual and regulatory structure of every project. OEMs mandate ASPICE assessments. ISO 26262 defines mandatory work products at every level of the V. Requirement quality at the left side of the V directly determines whether test cases on the right side can be derived, reviewed, and passed by an independent safety assessor. A requirement that is ambiguous at the system level propagates that ambiguity through subsystem, software, and component specifications, reaching integration testing as a defect that costs an order of magnitude more to fix than it would have cost to prevent.

The compounding problem is toolchain fragmentation. A modern Tier 1 or Tier 2 automotive supplier typically manages requirements across at minimum three incompatible systems: a customer-provided specification in Word or as a DOORS export, an internal DOORS NG or Polarion database for systems and safety engineering, and Jira or Azure DevOps for software teams. The normative reference — ISO 26262 Part 4 for system design, Part 6 for software, ASPICE SWE.1 through SWE.6 — lives as a PDF on a shared drive, manually referenced but never systematically linked to project requirements. The result: nobody can answer "which ISO 26262 Part 6 requirements does our software specification currently satisfy?" without a week of manual tracing.

Existing RE tooling addresses data storage and traceability, but not intelligence. DOORS NG stores requirements and manages baselines. Polarion adds ALM workflows. Neither tool tells you that system requirement SR-0445 contradicts safety goal SG-012, that 35% of your software requirements are duplicated between the feature module and the integration module with slight wording differences, or that your software specification has no requirements covering the Degraded Operation behaviour mandated by ISO 26262-6 §8.4.5. That analysis is left to senior safety engineers working at the limits of what a person can hold in memory across a 12,000-requirement project.

The V-Model context

The pipeline is designed around the automotive V-Model. Every requirement in the system has a position on the left side of the V, and the pipeline's analysis is V-Model-aware: it knows that a stakeholder requirement at the top must be traceable down through system, subsystem, and software requirements to component-level specifications, and that each level has corresponding test obligations on the right side.

Normative sources as requirements

The most significant structural gap in automotive RE tooling today is the treatment of normative standards. ISO 26262, ASPICE (Automotive SPICE), AUTOSAR specifications, and OEM-specific quality norms (e.g., VDA standards, customer-specific FMEA requirements) define mandatory work products, process requirements, and technical constraints that every project must satisfy. But these norms are referenced as documents, not as machine-readable requirements — which means coverage against them is tracked manually, incompletely, or not at all.

The pipeline ingests normative sources as structured requirement sets alongside project requirements. Each clause of a referenced standard that creates an obligation is parsed into a normative requirement atom and stored in the same canonical schema as project requirements. This enables two capabilities not available in any existing commercial RE tool:

  • Normative coverage analysis — which clauses of ISO 26262 Part 6 are addressed by at least one software requirement in your project specification? Which are not covered at all?
  • Cross-source contradiction detection — does any project requirement contradict a normative clause? For example, a performance requirement that makes a mandated safety monitoring behaviour physically impossible to implement within the required response time.
Normative source What is parsed Analysis it enables
ISO 26262 (Parts 3, 4, 6, 8) Work product requirements, technical safety requirements templates, ASIL-tagged shall-statements, and process obligations per development phase. Completeness gap check per ASIL level; contradiction detection between project requirements and safety norm; ASIL decomposition consistency verification.
ASPICE SWE.1–SWE.6 Process outcomes and work product requirements per capability level (CL2 / CL3); traceability obligations between process areas. Identify which ASPICE process outcomes are not covered by any project requirement or work product; flag before a formal assessment.
AUTOSAR specifications Interface contracts, BSW module requirements, and RTE behaviour constraints from AUTOSAR Classic and Adaptive specifications. Detect project software requirements that contradict AUTOSAR interface specs; identify missing AUTOSAR-mandatory work products.
OEM / customer norms Customer-specific quality requirements (e.g., VDA 6.3, OEM functional safety addenda, customer FMEA requirements) provided as structured documents or DOORS exports. Cross-source contradiction with project requirements; coverage gap identification before customer submission.
UNR / ECE regulations UN Regulations (e.g., UNR 155 cybersecurity, UNR 156 software updates) parsed to obligation-level requirement atoms. Verify that project cybersecurity and software update requirements cover the mandatory obligations of the applicable UN Regulation.

Normative sources are versioned in the pipeline: when a new edition of ISO 26262 or a revised AUTOSAR specification is released, the updated normative atoms are imported and a delta analysis flags which previously covered clauses are now uncovered or have changed in a way that may affect existing project requirements.

Stage 1 — normalisation

The first challenge in cross-source requirement analysis is that every source has a different schema. A DOORS module has attributes (ID, type, ASIL, status, rationale). A Polarion work item has a description and structured fields. A Word document has headers and paragraphs with no schema. An ISO 26262 PDF clause has normative weight but no machine-readable ID. Before any analysis is possible, all sources — project and normative alike — are mapped to a shared canonical form.

The normalisation engine uses an LLM to parse each incoming requirement and extract a structured canonical record:

Canonical field Description Extraction approach
statement The core shall/must/should statement, rewritten to INCOSE-compliant single-sentence active voice if necessary. Original text preserved separately. LLM extraction + rewrite; diff between original and rewrite shown in review UI
actor The system, subsystem, component, or role that must satisfy the requirement. NER + LLM resolution against system architecture taxonomy
condition The precondition or operational context under which the requirement applies (e.g., "during degraded operation mode"). LLM extraction; null if unconditional
measurable_criterion The quantitative or testable acceptance criterion. Flagged as missing if absent. LLM extraction; quality flag raised if none found
asil ASIL level (QM / A / B / C / D) extracted from source attributes or inferred from context. Used in ASIL consistency checks. Extracted from DOORS/Polarion ASIL attribute; LLM inference for unstructured sources; flagged for human confirmation if inferred
v_model_level Position in the V-Model: Stakeholder / System / Subsystem / Software / Component. Determines which analysis modules apply and which traceability links are expected. Extracted from module metadata or LLM classification; used for cross-level consistency analysis
norm_ref Reference to the normative source clause this requirement satisfies or originates from (e.g., ISO 26262-6:2018 §8.4.5, ASPICE SWE.1 BP3). Enables bidirectional normative traceability. Populated from normative atom matching; LLM similarity search against normative store; shown in review UI for engineer confirmation
requirement_type Functional, non-functional (performance / safety / security / usability), interface, constraint, or process (ASPICE work product obligation). LLM classification against taxonomy; cross-checked with v_model_level
source_ref Original source system, ID, module, and version. Full traceability back to origin. Populated from connector metadata; immutable
quality_flags List of detected quality issues: ambiguous subject, missing criterion, compound statement, passive voice, missing ASIL, untestable modal, normative gap. Rule-based + LLM quality classifier; each flag becomes a finding in the HITL queue

Every normalisation call is traced in Langfuse: the original text, the LLM prompt, the extracted canonical record, confidence scores for each field, and any quality flags. For ISO 26262 Part 2 (Management of Functional Safety) compliance, this trace constitutes the documented evidence that AI-assisted requirement processing was subject to human verification — a requirement for any safety-relevant AI tool in the development process.

Stage 2 — analysis modules

Once requirements are normalised and embedded, five analysis modules run on demand or on a configurable schedule. Each module produces structured findings that enter the human-in-the-loop review queue rather than being applied automatically.

Similarity analysis

Identifies requirements that express the same or overlapping intent across sources — potential duplicates between DOORS and Polarion, inconsistent rewrites of the same normative obligation, or requirements that constrain the same system behaviour from different V-Model levels without the expected traceability link.

The similarity pipeline runs in two passes. A fast embedding-based nearest-neighbour search retrieves candidate pairs above a configurable cosine similarity threshold. An LLM then classifies the relationship:

Similarity class Definition Recommended action
Duplicate Identical or near-identical intent. One requirement is redundant. Merge candidate routed to HITL review; engineer confirms or dismisses
Refinement One requirement is a specific instance of the other. Both are valid; a traceability link should exist between V-Model levels. Missing traceability link flagged; HITL review confirms the parent-child relationship
Normative duplicate Project requirement expresses the same obligation as a normative atom but is not formally linked to it. norm_ref link proposed; safety engineer confirms in HITL UI; contributes to normative coverage score
Coincidental High lexical similarity but different intent. No relationship required. Dismissed in HITL review; dismissal reason stored for classifier improvement

Contradiction detection

Identifies requirements that cannot both be satisfied simultaneously, including contradictions between project requirements and normative source clauses. In automotive development contradictions at the system level propagate down the V-Model and manifest as integration test failures or ASPICE assessment findings.

Contradiction type Automotive example Detection approach
Direct logical conflict "The BCM shall disable all non-safety-critical power consumers within 50 ms of detecting undervoltage" vs. "The gateway module shall maintain CAN communication for 200 ms after power loss to complete pending diagnostic frames." LLM logical entailment check on normalised statement pairs with system context
Quantitative incompatibility System requirement: "End-to-end latency for safety-critical path shall not exceed 10 ms." Software requirement (separate module): "Safety monitor watchdog cycle time shall be 8 ms" — leaving 2 ms budget for all other processing, contradicting throughput requirements elsewhere. Numeric constraint extraction across all requirements sharing an actor; arithmetic consistency check; LLM confirmation
Project vs. normative conflict Project requirement: "Fault detection shall be performed during scheduled maintenance only." ISO 26262-6 §8.4.4: "Fault detection shall occur at a rate commensurate with the safety goal response time." The project requirement makes the normative obligation impossible to satisfy. LLM comparison between project requirements and linked normative atoms; flagged with the specific standard clause reference
ASIL scope conflict Subsystem requirement tagged ASIL B shares an interface with a component requirement tagged QM, without documented freedom-from-interference justification — a direct ISO 26262-9 violation. ASIL attribute extraction across interface-sharing requirements; rule-based check for undocumented ASIL drops at interfaces

ASIL consistency checking

Verifies that ASIL assignments are consistent across the V-Model levels. Common failures include: an ASIL D safety goal decomposed into two ASIL B requirements without a documented independence argument, a software requirement with a higher ASIL than its parent system requirement (impossible decomposition), or ASIL-tagged requirements allocated to components without a corresponding hardware-software interface specification.

This analysis is deterministic — it applies ISO 26262-9 decomposition rules programmatically across the ASIL graph — and does not rely on LLM judgement for the core rule check. LLM is used only to explain the finding in plain language for the HITL review UI.

Completeness gap analysis against norms

Measures coverage of the project requirement set against the normative requirement atoms ingested from ISO 26262, ASPICE, and any applicable OEM norms. For each normative atom the pipeline reports: covered (at least one project requirement satisfies it), partially covered (a project requirement addresses the same topic but does not fully satisfy the obligation), or uncovered (no project requirement exists for this normative obligation).

Coverage is reported per standard part and per V-Model level. An ASPICE CL3 assessment preparation run, for example, reports which SWE.1 through SWE.6 process outcomes are satisfied by existing work products and which will generate assessment findings.

Divergence scoring

Tracks specification drift between two versions or between two parallel sources — for example, the OEM-provided customer specification versus the internally maintained DOORS baseline, or the locked project start specification versus the current state after a change request series. Three divergence levels are analysed:

  • Structural divergence — requirements present in one set but absent in the other; functional areas that have grown or disappeared.
  • Semantic divergence — requirements that nominally correspond but have drifted in intent. Quantified as a semantic drift score (0–1) per requirement pair.
  • Normative divergence — normative coverage that was satisfied in the baseline but is no longer satisfied in the current version, indicating a regression in standards compliance.

Stage 3 — human-in-the-loop review UI

Every finding produced by the analysis modules enters a structured review queue before any action is taken. No requirement is automatically changed, merged, written back to DOORS, or linked to a normative source without an engineer confirming the finding in the review UI. This is a hard architectural constraint: the pipeline is an AI-assisted analysis tool, not an autonomous authoring agent.

The HITL principle matters beyond process hygiene. ISO 26262 Part 2 §6 and the EU AI Act (Art. 14) both require that AI systems influencing safety-relevant decisions operate under meaningful human oversight. A fully automated requirement improvement pipeline in a functional safety context is not compliant. The HITL UI provides the documented review record that both frameworks require.

Improvement proposals in the review UI

For quality-flagged requirements, the improvement engine generates a rewritten version correcting the identified problem while preserving intent. The proposal is presented in the finding detail screen alongside the original, never committed without explicit reviewer acceptance. The table below shows the quality issues handled:

Quality issue What the engine does Automotive example
Ambiguous actor Identifies the implied actor from module context and system architecture taxonomy; makes it explicit. "Faults shall be detected and reported" → "The Diagnostic Manager component (ASIL B) shall detect and report all monitored faults to the DEM within one watchdog cycle (≤ 8 ms)."
Missing measurable criterion Proposes a quantitative criterion based on the requirement type, any figures in adjacent requirements, and referenced normative clauses (e.g., ISO 26262-mandated response times). "The system shall respond to activation requests quickly" → "The body control module shall respond to door lock activation requests within 150 ms under all operating conditions defined in SR-0012."
Compound statement Splits multi-requirement statements into separate atomic requirements, each with its own ID and individual ASIL assignment. One requirement covering detection, logging, and notification split into three atomic requirements with independent ASIL assignments where applicable.

Why no existing tool does this

From a market perspective, the tools currently available to automotive suppliers address individual parts of this problem but none combines them. Understanding the market gap is critical to positioning this engagement: the Requirement Intelligence Pipeline is not a marginal improvement on an existing tool category — it occupies a space where no commercial product exists.

No cross-module contradiction detection. No normative source ingestion. Traceability links are manually created. Quality checking is limited to attribute completeness (field is empty / not empty), not semantic quality.

The gap is structural. The incumbent RE tools (DOORS, Polarion) are storage and traceability systems — they were designed in the 1990s and 2000s for a world where semantic analysis was computationally infeasible. The normative linking gap exists because standards bodies do not publish machine-readable requirement atoms: ISO 26262 is a PDF. The HITL governance gap exists because no supplier-facing tool has invested in a review workflow that combines AI findings with an audit-compliant confirmation mechanism suitable for functional safety contexts.

For an MHP client in automotive, this means the competitive positioning is clear: the Requirement Intelligence Pipeline is not displacing a tool the client already owns. It is providing a capability layer that the client's existing toolchain will never provide, built specifically for the DOORS/Polarion/ISO 26262/ASPICE context that German Tier 1 and Tier 2 suppliers operate in.

What makes this different

  • Built for the automotive V-Model, not adapted to it — the canonical schema includes ASIL, v_model_level, and norm_ref as first-class fields. Analysis modules understand the cross-level traceability obligations and ASIL decomposition rules that govern automotive development. Generic RE quality tools apply generic rules; this applies ISO 26262 and ASPICE rules.
  • Normative sources are requirements, not documents — ISO 26262 and ASPICE clauses are parsed to machine-readable normative atoms and stored in the same analysis engine as project requirements. Cross-source contradiction detection and normative coverage analysis are structurally impossible without this step. No commercial RE tool provides it.
  • Human-in-the-loop is the architecture, not an option — every finding enters a review queue. No requirement is changed without engineer confirmation. The review UI provides the documented decision record that ISO 26262 Part 2 and the EU AI Act require for AI-assisted safety-relevant processes. This is an architectural constraint, not a feature that can be disabled for speed.
  • Fills the gap between DOORS and nothing — DOORS NG is the standard, and it will not be replaced. The pipeline is a service layer on top of DOORS (and Polarion), adding analysis and governance that IBM has no roadmap to deliver. The client keeps their existing toolchain investment and adds the intelligence layer without a migration project.
  • Traceable AI decisions for functional safety — every LLM call, every HITL decision, and every accepted improvement is logged in Langfuse with full context. The audit trail is structured for export to a safety case management tool or functional safety assessment evidence package.
  • Source-agnostic normalisation means cross-tool contradictions surface — the most dangerous contradictions in automotive RE are between the customer specification (in Word), the system requirement (in DOORS), and the software requirement (in Polarion). They are in different tools, different schemas, different teams. The normalisation step makes them comparable for the first time.

Common questions

Do our requirements have to leave our site for the LLM API calls?
Not necessarily. We support deployment with a self-hosted model (Llama 3, Mistral, or a private Azure AI deployment) running entirely within your infrastructure. In that configuration, no requirement text leaves your environment. For projects under export control or with OEM-mandated data residency requirements, this is the default deployment path we recommend.

We use DOORS NG — will engineers have to learn a new authoring tool?
No. Engineers continue to author in DOORS NG exactly as today. The review UI is used only to triage AI-generated findings and accept or dismiss improvement proposals. Accepted improvements are written back to DOORS as draft items — the engineer approves the draft in DOORS using the existing DOORS change control process. The pipeline is an additional service, not a replacement.

How do we keep the normative source library current when ISO 26262 or ASPICE is revised?
MHP maintains the normative atom library. When a new edition of ISO 26262 or a revised ASPICE process reference model is released, we update the library and deliver a delta analysis: which previously covered clauses are now uncovered or changed in a way that affects existing project requirements. The delta analysis is delivered via the review UI as a batch of normative-gap findings for the FSM and RE lead to review.

What is the false-positive rate on contradiction detection?
After calibration, typically 15–25% of flagged pairs are false positives reviewed and dismissed by engineers. This is deliberately conservative: a missed real contradiction in an ASIL C system costs orders of magnitude more than a 30-second review of a false positive. Dismissed findings are stored and used to improve the classifier across subsequent runs, reducing the false-positive rate over time.

Can we trigger the pipeline from our CI/CD or milestone gate process?
Yes. The pipeline exposes a REST API endpoint that any authorised caller can invoke. A common integration pattern is to trigger a scoped analysis (e.g., all requirements changed since the last baseline) as part of a milestone gate check, with the results delivered to the review UI and optionally posted as comments in the change management tool. The CI integration example is included in the API documentation delivered at handover.

How is the HITL review UI evidence used in the functional safety case?
The review UI exports a structured audit log of every finding, every reviewer decision (accept / dismiss / escalate), the reviewer identity, and the timestamp. This log is formatted for direct inclusion in the safety case as evidence that AI-assisted requirement analysis was subject to documented human verification — satisfying the human oversight requirement in ISO 26262 Part 2 §6 for AI-assisted safety processes. The ASIL consistency confirmation records from the HITL UI are exported as a structured evidence pack separately, formatted for the safety case argumentation.
