Details

The problem

AI agents are different from conventional services in ways that break standard SRE practices. A microservice either returns 200 or it doesn't. An agent can return 200, take the correct code path, and still produce a wrong answer — one that a user accepts and acts on before the error surfaces. Error rates measured at the infrastructure layer tell you almost nothing about whether the agent is actually working.

Failures are also non-deterministic. The same input can produce different outputs on subsequent runs. Traditional incident root cause analysis — reproduce the failure, isolate the cause, fix and verify — does not directly apply. Without Langfuse traces and a structured approach to probabilistic failure investigation, on-call engineers are flying blind.

And the cost model is unlike any other service: token consumption, not compute, is the primary cost driver, and a single misconfigured agent can generate five-figure API bills in hours. An ops practice without per-workload cost attribution and budget alerting is not managing its exposure — it is discovering it on the monthly invoice.

Token cost per request is invisible in standard cloud cost reports. Without Langfuse cost tracking integrated into cost dashboards, AI spend cannot be managed at the workload level.

SLO design for AI workloads

We design a two-tier SLO model for each agent workload:

  • Infrastructure SLOs — conventional reliability indicators: request success rate (non-5xx), p95 and p99 latency, agent availability (uptime). These are measured from infrastructure metrics and Langfuse trace completion rates.
  • Quality SLOs — AI-specific reliability indicators: task completion rate (did the agent complete its assigned task?), grounding score (is the output supported by retrieved context?), guardrail pass rate (what fraction of runs hit a guardrail?), and user satisfaction signal (CSAT or thumbs-up/down). Measured from Langfuse quality scores.

Error budgets are calculated separately for infrastructure and quality SLOs. A quality error budget burn is the signal that triggers a prompt engineering sprint or a retrieval pipeline review — the same way an infrastructure error budget burn triggers a reliability engineering sprint.

What makes this different

  • Quality SLOs, not just infrastructure SLOs — we define reliability targets that measure whether the agent is doing its job, not just whether the container is running. A quality error budget burn is as actionable as an availability burn.
  • Langfuse-native runbooks — runbooks written for engineers who will diagnose failures from Langfuse traces, not from application logs. The first step for every alert is a direct link to the failing trace category in Langfuse.
  • Prompts treated as code — the deployment pipeline applies the same quality gates and canary stages to system prompt changes as to application code changes. A prompt regression is caught before it reaches 100% of traffic.
  • Cost operations as a first-class discipline — per-workload cost dashboards and budget alerts are part of the engagement scope, not an afterthought. Cost anomaly detection runs in the same observability stack as quality anomaly detection.

Client story

E-commerce platform, 450 employees, 4 customer-facing agent workloads — had four agents in production (product search, returns assistant, order tracking, and customer support triage) with a three-person ops team responsible for all four. The ops team had no AI training, no agent-specific runbooks, and no visibility into per-workload LLM spend. MTTR for agent incidents was averaging 4.5 hours because diagnosing failures required escalating to the AI engineering team every time.

We ran a 9-week engagement: defined 12 infrastructure and quality SLOs across the four workloads, built Langfuse-native runbooks for the 8 most common alert types, deployed a canary pipeline for prompt and guardrail changes, set up per-workload cost dashboards with budget envelope alerts, and ran a 4-hour ops training session. MTTR dropped to 1.6 hours within 30 days as the ops team resolved L1 incidents from the runbooks. Two cost anomalies were detected and addressed in the first 60 days before they reached the monthly invoice. Zero quality regressions reached 100% of traffic in the three months post-deployment.

Risks we mitigate

  • Prompt regression reaching full traffic — without a canary pipeline, a system prompt change that degrades quality reaches all users immediately. Canary stages with automated quality analysis catch regressions before full rollout.
  • Runaway LLM spend — without per-workload cost attribution and budget alerts, cost anomalies are discovered at month end, not in real time. Budget envelope alerts detect anomalies within minutes of the spend pattern emerging.
  • Ops team burnout on unmanaged AI incidents — ops engineers who cannot diagnose AI failures independently escalate everything, creating a bottleneck on the AI engineering team. Langfuse-native runbooks and training resolve this structural dependency.

Common questions

We don't have Langfuse yet — can we still do this engagement?
Langfuse is a prerequisite for the Langfuse-native runbooks and quality SLOs. We can deploy Langfuse as part of this engagement (typically 1–2 days) or scope it as a preceding Enterprise AI Harness sprint. The deployment pipeline and cost dashboards can be delivered without Langfuse but lose the quality-signal integration.

How do SLOs work for non-deterministic systems?
Quality SLOs are probabilistic: "90% of agent runs should score ≥ 0.85 on the grounding metric over any 7-day window." The 10% budget absorbs natural variance. What triggers an error budget burn is a statistically significant downward shift in the quality distribution — the signal that something has changed in the system, not natural noise.

What if the ops team has no AI background?
The runbooks and training are designed for engineers who have never worked with LLMs. The first three steps of every runbook are: (1) open the Langfuse trace, (2) find the failing span, (3) look up the span type in the runbook. Domain knowledge of AI is not required. Understanding how to read a structured trace log is sufficient.
