Details

The problem

Most enterprises building their first three AI agents do so in isolation — each team picks its own orchestration framework, deploys to its own container, manages its own secrets, and connects directly to whatever APIs it needs. At one or two agents this is survivable. At ten it is an operational crisis: nine different deployment pipelines, no shared identity model, cost attribution impossible, and every outage requiring a different runbook.

The foundational architecture question — how does this enterprise run AI agents as a platform, not as a collection of one-offs? — almost never gets answered before the first incident demands it. By that point, retro-fitting isolation, security, and governance onto running systems costs three to five times what designing for them upfront would have.

The architecture layers

A production-grade agentic platform has five layers. Each layer has distinct design concerns and failure modes. The engagement designs all five in sequence and produces deployable Infrastructure-as-Code for each.

What you get

  • Platform architecture document — C4-level diagrams covering context, containers, and components for all five layers, with technology choices justified against your constraints (cloud provider, data residency, compliance framework).
  • Infrastructure-as-Code baseline — Terraform or Pulumi modules for the compute and identity layers, ready to deploy in your target environment. Includes namespace structure, RBAC policies, resource quotas, and secret management configuration.
  • Agent identity model — documented service-account schema for agent identities: naming convention, role hierarchy, permission matrix by agent class, rotation policy, and IdP integration guide.
  • Environment strategy — defined dev / staging / prod topology with promotion gates, data masking rules for lower environments, and traffic-mirroring design for safe production validation.
  • Architecture decision record (ADR) set — one ADR per major design choice (orchestration framework, memory store, API gateway, observability platform) with rationale, alternatives considered, and review cadence.
  • Onboarding template — a standardised checklist for registering a new agent workload into the platform, covering all five layers, so future teams do not have to re-derive the architecture from scratch.

What makes this different

  • Platform thinking, not agent thinking — most architecture reviews focus on a single agent. We design for the fleet: shared identity, shared tool registry, shared observability, with isolation between workloads built in from the start.
  • IaC delivered, not just diagrams — the engagement produces deployable Terraform or Pulumi modules, not a slideware architecture. Your team can provision the baseline environment from day one of implementation.
  • Constraint-driven design — we start from your non-negotiables (data residency, cloud provider, compliance framework) rather than a generic reference architecture. Every technology choice is traceable to a constraint or a deliberate trade-off.
  • ADRs as governance artifacts — architecture decision records created during the engagement become the living documentation your team uses to onboard new architects and justify future changes to regulators or internal review boards.

Client story

European manufacturing firm, 4 200 employees, 6 planned agent workloads — had two agent pilots live and four more in development across different business units, each deploying to its own Azure resource group with no shared infrastructure. The CTO's concern: by the time all six were live, the ops team would be managing six independent deployment pipelines, six secret stores, and six different approaches to connecting to the SAP ERP system.

We ran a 7-week architecture engagement and delivered: a Kubernetes-based platform design with namespace isolation per business unit, a unified MCP server registry for SAP and the document management system, a Terraform module set covering identity, compute, and networking, and an agent onboarding template. The four in-development teams adopted the platform baseline rather than building their own infrastructure. Estimated engineering cost avoided across the four teams: 22 person-weeks in the first six months. First production incident in the shared platform environment: zero in the first 90 days.

Risks we mitigate

  • Privilege escalation across workloads — without a shared identity model, a compromised agent service account in one workload can pivot to another. A defined RBAC model and per-agent service accounts with least-privilege scoping eliminates the lateral movement path.
  • Unplanned infrastructure cost growth — ad-hoc deployments without resource quotas routinely run 2–3× over budget as agent workloads scale. Platform-level cost attribution and quotas prevent this.
  • Architecture lock-in — early framework choices (orchestration library, vector store, cloud service) become expensive to change once three or four agents depend on them. ADRs with review cadences ensure choices are revisited deliberately rather than inherited accidentally.
  • Environment contamination — agents writing to production data stores from a development environment is a recurring incident in teams without a defined environment strategy. Namespace isolation and data masking rules in lower environments eliminate this risk class.

Common questions

We're already on AWS — does the architecture lock us to a cloud provider?
No. The platform design uses provider-managed services where they genuinely reduce operational burden (managed Kubernetes, managed secret store), and open-source components (Langfuse, MCP servers, Postgres) where portability matters. The IaC modules are written for your current provider, with the ADRs documenting where vendor-specific choices were made and what the migration path would be.

Can we reuse this architecture for non-agent AI workloads?
Yes. The identity, compute, and observability layers apply to any ML or AI workload. The tool connectivity and state/memory layers are agent-specific but add no overhead to workloads that don't need them — they simply don't use those components. Most clients find the platform naturally absorbs their existing batch ML workloads without modification.

How does this relate to the Enterprise AI Harness?
This engagement designs the foundational platform layers — compute, identity, networking, and state. The Enterprise AI Harness adds governance, guardrails, and quality controls on top of a running platform. The two are sequenced: platform architecture first, then harness. If you already have a running platform with reasonable foundations, you can start directly with the harness.
