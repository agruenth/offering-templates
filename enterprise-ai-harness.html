The problem

Most enterprises now have at least three AI agent pilots running. Almost none of them are production-safe. The gap is not model capability — it is infrastructure. Agents call external tools with no permissions model, access data lakes with no column-level controls, log nothing the compliance team can read, and have no mechanism to stop or escalate when they hit an unexpected state. A single runaway agent can burn €50 K in API tokens, exfiltrate a customer dataset into a third-party LLM prompt, or trigger 2 000 downstream API calls before anyone notices.

The compounding problem: enterprises are deploying AI where deterministic automation would be safer, faster, and cheaper — and deploying deterministic automation where an agent's reasoning would actually add value. The result is systems that are simultaneously over-engineered and under-controlled. Without a principled deployment model that answers "when do we use an agent, when do we use a workflow, and how do we govern both," every AI initiative is a liability the CISO, CRO, and General Counsel will eventually block.

Pillar 1 — MCP: standard tool connectivity

The Model Context Protocol (MCP) is an open standard, introduced by Anthropic in 2024 and now adopted across the major LLM platforms, that defines a uniform interface between AI agents and the tools, data sources, and services they need to call. Think of it as USB-C for enterprise AI: instead of every agent implementing its own bespoke connector to your CRM, ERP, or file system, MCP servers expose those systems through a standard protocol that any compliant agent can use — with permissions, versioning, and schema validation built in.

Without MCP, enterprise tool connectivity is a sprawl of ad-hoc integrations: each agent team writes their own connectors, there is no central catalogue of what agents can access, and access control lives in comments rather than enforced policy. With MCP, the enterprise owns a curated server registry — each server exposes a defined set of tools with typed inputs, declared side-effects (read vs. write), and rate limits — and every agent accesses the world through that registry.

MCP concept What it does Governance value
MCP Server Exposes a set of tools (functions, data sources, services) through the standard protocol. One server per system of record (CRM, ERP, document store, etc.). Single integration point per system — access control, versioning, and schema validation in one place rather than scattered across agent codebases.
Tool definition Each tool declares its name, input schema, output schema, and whether it has side-effects. Agents see a contract, not an implementation. Agents cannot call undeclared operations. Destructive tools (delete, send, write) are flagged and require elevated authorisation.
Server registry A versioned catalogue of all MCP servers in the enterprise, with per-role access policies defining which agent identities can connect to which servers. Audit of "what could this agent have done" is answerable from the registry, not from reading source code.
Dry-run mode Write operations execute their validation and return a preview of the effect without committing the change. The agent must receive explicit approval to proceed. Eliminates unintended mutations. Approval events are logged to Langfuse as first-class trace events.

We design and deploy the MCP server layer for your environment: identifying the systems of record that agents need to reach, building or configuring MCP servers for each, defining the tool permission matrix by agent role, and wiring dry-run gates for all write operations. The result is a tool layer that any future agent can use on day one without a new integration project.

Pillar 2 — deterministic automations vs. agentic reasoning

Not every business process should involve an AI agent. The single most common architecture mistake in enterprise AI programmes is routing predictable, structured work through an LLM because it is technically possible to do so. LLM calls are probabilistic by nature: the same input can produce different outputs across runs. For process-critical work — invoice processing, compliance checks, order routing, contract clause extraction — that non-determinism is a defect, not a feature.

The harness introduces a deliberate routing layer that separates two classes of work:

Deterministic automation Agentic reasoning
When to use Structured inputs, predictable logic, identical output required every run. Examples: data transformation, rule-based routing, API orchestration, scheduled reporting. Ambiguous inputs, multi-step reasoning, context-dependent judgment. Examples: customer query handling, document summarisation, research synthesis, anomaly investigation.
Output guarantee Identical output for identical input. Errors are deterministic and reproducible. Output varies; quality governed by guardrails and quality gates rather than code logic.
Traceability Execution log: inputs, step results, outputs. Fully reproducible. Langfuse trace: prompt, model, tool calls, latency, cost, scores, human annotations.
Tooling n8n, Temporal, Airflow, custom workflow engines, RPA where legacy systems require it. LangGraph, LlamaIndex, custom Python loops, orchestrated via MCP tool layer.
Cost profile Near-zero marginal cost per run after setup. No LLM tokens consumed. LLM API cost per run; budget-envelope enforcement required.

In practice, the highest-value enterprise systems combine both: a deterministic workflow handles the structured backbone of a process (data retrieval, routing, writing results back to the system of record), while an agent handles the reasoning step in the middle (classifying an ambiguous input, drafting a response, deciding which path to take). This hybrid pattern gives you the reliability of a workflow with the intelligence of an agent — and the cost profile of the former wherever AI is not adding marginal value.

Pillar 3 — full traceability with Langfuse

Langfuse is an open-source LLM observability platform that gives every agent run a structured, queryable trace: from the initial user input through every reasoning step, tool call, model invocation, and guardrail decision, to the final output and its quality score. It is the audit trail, the debugging tool, and the continuous-improvement engine for your agent fleet — all in one.

We deploy Langfuse in your infrastructure (self-hosted or managed) and instrument every agent workload so that nothing happens without a trace. The key tracing primitives:

Langfuse concept What it captures Use in governance
Trace One complete agent session: user ID, session ID, initial input, all intermediate steps, final output, total latency, total cost. The primary audit unit. "Show me everything this agent did for user X on date Y" is a single query.
Span Each step within a trace: LLM call, tool call, guardrail evaluation, retrieval, deterministic workflow handoff. Each span has its own latency, cost, and input/output snapshot. Root-cause analysis for failures without reading logs. "The agent took 12 seconds — which step was slow?" answered in the Langfuse UI.
Score Numeric or categorical quality score attached to a trace or span: LLM-as-judge evaluation, human annotation, CSAT feedback signal, guardrail pass/fail. Quantified quality over time. Regression detection: "Average score for the customer-support agent dropped from 0.87 to 0.71 after the prompt change on Tuesday."
Dataset & experiment A curated set of inputs with expected outputs, used to evaluate prompt or model changes before deployment. Langfuse runs the experiment and surfaces score deltas. Safe prompt engineering: no change goes to production without a scored experiment showing it does not regress quality or guardrail coverage.
Cost tracking Token usage and API cost per trace, span, user, and agent — aggregated to daily/monthly dashboards with per-workload budget thresholds and alerts. Compliance-ready spend attribution. Budget overruns trigger alerts before they hit the invoice.

The Langfuse traces produced by the harness are exportable to your SIEM or data warehouse. For regulated industries, we configure trace retention policies, access controls (only named principals can read traces containing PII), and an immutable export to cold storage on a configurable schedule — providing the tamper-evident audit log that compliance frameworks require.

Pillar 4 — customer engagement quality gates

When AI generates content that reaches an end customer — a support response, a product recommendation, a contract summary, a generated report — the enterprise needs a quality gate between the model output and the delivery channel. Without it, a hallucinated clause ends up in a client document, a toxic response reaches a support queue, or an off-brand message goes out under the company's name.

Quality gates are configurable checkpoints that evaluate every output before it leaves the system. They operate on a threshold model: outputs above the threshold are delivered automatically; outputs below threshold enter a human review queue. The threshold is tuned per use case — a customer-facing legal summary has a higher bar than an internal search snippet.

Gate type What it checks How it works
Factuality / grounding check Does the output make claims that can be verified against the retrieved source documents? Are citations accurate? LLM-as-judge: a second, lightweight model call evaluates the output against the context window and returns a grounding score (0–1). Outputs below threshold flagged for human review.
Tone & brand compliance Does the response match the defined communication guidelines — formality level, prohibited phrases, brand voice? Classifier trained on approved vs. rejected examples from your own communication archive. Tunable per channel (email vs. chat vs. document).
Completeness check Does the output address all the sub-questions or requirements in the input? Are any required fields missing? Structured schema validation for templated outputs; LLM-as-judge coverage score for open-ended responses.
PII & sensitivity scan Does the output contain personal data, account numbers, internal system names, or other content that must not reach an external recipient? Regex + NER + fine-tuned classifier. High-confidence detections block delivery automatically; low-confidence detections route to review.
CSAT feedback loop Did the customer signal satisfaction or dissatisfaction with this response? Does negative feedback correlate with specific agents, prompts, or model versions? CSAT signal ingested as a Langfuse score on the originating trace. Negative-signal traces are surfaced for review and optionally used as training data.

Quality gates are not a one-time configuration — they are a continuous improvement loop. Every human override, every CSAT signal, and every LLM-as-judge score is a labelled data point in Langfuse. Over time this corpus powers prompt refinement, threshold tuning, and model evaluation: the quality of customer-facing AI improves measurably, with every change backed by scored evidence rather than intuition.

Pillar 5 — guardrails across the AI programme

Guardrails are not just technical filters on individual agents. In a mature enterprise AI programme they operate at three levels simultaneously:

  • Initiative-level guardrails — what AI is and is not permitted to do in your organisation at all. Defined by the AI governance board, encoded as policy: which data categories may not enter an LLM prompt, which decisions may never be fully automated, which channels require human sign-off before AI content is delivered. These are non-negotiable constraints that apply to every agent regardless of use case.
  • Agent-level guardrails — input and output filters specific to an agent's role and data access. A customer-support agent has different PII rules than an internal research agent. A financial-advice agent has stricter factuality thresholds than an internal knowledge-retrieval agent. Guardrails are parameterised per agent identity in the registry.
  • Run-level guardrails — dynamic checks applied at execution time based on context: the identity of the requesting user, the sensitivity classification of the data retrieved, the cost already consumed in the session. A run that has already spent 80% of its budget envelope is automatically throttled; a run that retrieves a document tagged as "confidential" triggers an additional output scan before the response is released.

The guardrail configuration is stored as code, versioned in your repository, and tested in CI against a red-team prompt suite before any change reaches production. Guardrail hit events are first-class spans in Langfuse — searchable, aggregable, and alertable. "Guardrail X fired 40% more this week than last" is an alert, not a surprise discovered during an audit.

Common questions

We're not using Anthropic models — does MCP still apply?
Yes. MCP is an open protocol supported by OpenAI, Google DeepMind, and all major orchestration frameworks (LangChain, LangGraph, LlamaIndex, AutoGen). The MCP server layer we build is model-agnostic: the same servers work regardless of which LLM your agents call. You also benefit from a switching option — changing the underlying model does not require rebuilding your tool integrations.

How do we decide which processes should be deterministic vs. agentic?
We run a structured classification workshop in Phase 2, scoring each process on three dimensions: input variability (how structured?), output criticality (what's the cost of a wrong answer?), and reasoning complexity (does this require judgment or just logic?). High-structure, high-criticality work becomes deterministic; high-variability, judgment-intensive work becomes agentic. Most enterprises find 40–60% of their current "AI" workloads are better served by a workflow engine.

Can we self-host Langfuse, or does it need a cloud account?
Langfuse is open source and we deploy it entirely within your infrastructure — Kubernetes, a VM, or a managed Postgres instance. No trace data leaves your environment. For enterprises with strict data residency requirements, this is the default deployment. We also support Langfuse Cloud for teams that prefer managed operations, with appropriate data processing agreements in place.

How much does the harness add to agent latency?
Input guardrails add 80–150 ms; output guardrails and quality gates add 100–300 ms depending on the gate complexity. For async workloads (document processing, scheduled reports) this is imperceptible. For synchronous customer-facing agents, we run quality gates in parallel with response streaming to reduce the net overhead to near zero. Langfuse tracing adds < 5 ms (asynchronous SDK call).

What if we need to onboard new agents after the engagement ends?
The agent onboarding runbook covers all five harness pillars: how to register MCP tools, configure guardrails, instrument Langfuse, and set quality gate thresholds. Your engineering team can onboard a new agent in under one day. For novel agent architectures or high-risk use cases we offer a half-day remote review, typically needed once or twice in the first year.

Can we pilot just one or two pillars first?
Yes. The most common starting point is Langfuse + guardrails (Pillars 3 and 5) — it requires no changes to existing agent code and immediately gives you the audit trail and incident detection that compliance needs. MCP and quality gates follow once the baseline observability is in place. We can scope a 4-week pilot covering these two pillars as a standalone engagement that gates the full harness.
