Details

The problem

AI agent programmes that succeed at the pilot stage tend to hit the same scaling problem at production: cost per transaction is acceptable at 1 000 runs per month and alarming at 100 000. Unlike conventional software where marginal cost is near zero, every agent run consumes tokens — and token prices, while falling, still make an unoptimised production agent materially expensive at enterprise scale.

Most agent implementations are not engineered for cost efficiency because the design priority during development is correctness, not economics. Frontier models are used because they are reliable; long system prompts are used because they are thorough; no caching is implemented because invalidation is complex. These choices make perfect sense during development. They make poor sense at scale.

The typical enterprise agent fleet has 30–40% of its LLM spend attributable to three optimisable patterns: tasks that do not require a frontier model, static context that qualifies for prompt caching, and queries that could be served from a semantic cache. Finding and addressing these patterns — without regressing quality — is a mechanical process once you have the right telemetry.

The optimisation process

Every optimisation decision is evidence-based. We do not apply a lever because it is available; we apply it because the Langfuse telemetry shows that it is the right lever for the specific workload, and we validate the application against a quality eval set before deploying to production.

  • Phase 1 — cost attribution and profiling: use Langfuse to decompose total LLM spend by workload, by agent, by span type, and by model. Identify the top three cost and latency drivers. Establish unit cost baselines (cost per agent run, cost per user query, p95 latency per workload).
  • Phase 2 — opportunity sizing: for each optimisation lever, size the addressable opportunity from the Langfuse data. "15% of CRM lookup spans use GPT-4o; a quality eval shows GPT-4o-mini produces equivalent output" becomes a sized saving, not a hypothesis.
  • Phase 3 — implementation with quality gating: each optimisation is implemented and validated against the quality eval dataset before deployment. A canary stage confirms no quality regression in production before full rollout.
  • Phase 4 — continuous monitoring: cost-per-run dashboards in Grafana track the achieved savings over time. Quality SLOs ensure that savings do not come at the cost of output quality. Monthly unit economics reports show the trajectory.

Risks we mitigate

  • LLM cost becoming a business model risk — at €200 K+ annual LLM spend, cost per transaction is a pricing and margin input, not just an infrastructure line item. Without per-workload attribution and a reduction roadmap, this risk is invisible until it is structural.
  • Premature model tiering degrading quality — the most common optimisation mistake is switching to a smaller model without quality validation. Every tiering decision in this engagement is gated by a quality eval; no token saving ships without a quality sign-off.
  • Missing prompt caching leaving easy money on the table — API-level prompt caching is available on every major LLM API and reduces cached token costs by 50–90%. It is the highest-ROI, lowest-risk optimisation available, and the most commonly not implemented simply because it was not on the development team's radar.

Common questions

Won't switching to a smaller model degrade quality?
Sometimes, yes — which is why every model tiering decision is validated against a quality eval dataset before deployment. We don't assume smaller models are adequate; we measure whether they are, for your specific task and data distribution. If the eval shows a quality gap, we do not tier the workload.

What is prompt caching and why haven't we implemented it already?
Anthropic, OpenAI, and Google all offer API-level prompt caching: if the first N tokens of a request match a previous request, the cached token costs are 50–90% lower than uncached. It is a single configuration change in most cases. It is not implemented by default because it requires prompt structure discipline (stable content at the top, variable content at the bottom), which development teams building for correctness rarely prioritise.

How do semantic caches handle cache invalidation?
We configure TTL-based invalidation (cache entries expire after a defined period) and event-based invalidation (cache is flushed when a dependent data source changes). The cache hit-rate dashboard shows cache age distribution, so stale hit rates are visible. For workloads where freshness is critical, we set conservative TTLs or disable semantic caching for those specific query types.
